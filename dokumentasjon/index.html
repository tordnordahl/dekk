A · Transaksjonsgrunnlag

For en potensiell kjøper

Dette dokumentet skal gjøre det mulig å vurdere produktet teknisk og kommersielt, overta produksjonsdriften og videreutvikle løsningen uten å være avhengig av muntlig kunnskap fra selger.

Det som overtas

PHP/Laravel-kodebase, database- og migreringsmodell, offentlig nettsted, webportal, mobil teknikermodus, kundeportal, REST API/OpenAPI, installer, oppdateringsverktøy, tester og denne håndboken.

Produktets posisjon

Multi-tenant SaaS for dekkhotell og dekkverksted, med hele flyten fra kunde og booking til lager, kontroll, mersalg, kommunikasjon og regnskapseksport.

Hva som ikke skal antas

Ingen separat native iOS/Android-kodebase er funnet i dette depotet. Stripe er ikke aktiv betalingsmåte. DekkPilot er ikke et fullverdig regnskapssystem.

Avgrensning

Den tekniske dokumentasjonen beskriver det som finnes i kodebasen. Kjøpesum, selskapsaksjer, kundekontrakter, historisk omsetning, domeneeierskap, varemerker og tredjepartslisenser må spesifiseres uttrykkelig i kjøpekontrakten og verifiseres separat.

Ikke bruk markedsføringspåstander som teknisk fasit. Kjøper bør kjøre testpakken, kontrollere produksjonsmiljøet og dokumentere hvilke immaterielle og operative eiendeler som faktisk følger handelen.

  • Felles applikasjon og database.
  • Forretningsdata avgrenses med organization_id.

  • Webserver/PHP kjører applikasjonen.
  • MySQL er autoritativ datakilde.
  • Scheduler må trigges hvert minutt.
  • Ekstern levering avhenger av kundens/providerens nøkler.
  • Regnskap mottar fakturagrunnlag via adapter.

Skaleringspunkter

  • Kø/statusmodeller for meldinger og eksport.

Anbefalt teknisk overtakelsesrekkefølge

  1. Signer avtale og databehandler-/konfidensialitetsgrunnlag.
  2. Frys en identifisert release og ta full, verifisert backup.
  3. Overfør depot, domener, hosting og administrative kontoer.
  4. Opprett kjøpers egne brukere før selgers tilgang fjernes.
  5. Roter DB-passord, APP-miljøhemmeligheter, API-nøkler og deploynøkler kontrollert. Bevar gjeldende APP_KEY til krypterte data er migrert.
  6. Kjør migreringsstatus, helsesjekk, testpakke og manuell smoke-test.
  7. Test backup/restore, cron, kø, e-post og én sandbox-regnskapseksport.
  8. Dokumenter akseptert tilstand og start overvåket driftsperiode.
Ikke bytt APP_KEY ukritisk. Den eksisterende nøkkelen dekrypterer lagrede integrasjonshemmeligheter. Nøkkelrotasjon krever planlagt re-kryptering.

D · Produktutvikling

Videreutvikling og anbefalt prioritering

1. Produksjonshardening

CI/CD, staging, automatisk testkjøring, sentral logging, oppetidsmåling, alarmer, dokumentert restore og regelmessig sikkerhetsgjennomgang.

2. Integrasjoner

Fullfør provider-sandbox og kontraktstester for Fiken/Tripletex, leveringswebhooks, idempotens og tydelig operatørhåndtering av feil.

3. Mobil produktflate

Bruk OpenAPI som kontrakt for en separat iOS/Android-klient. Prioriter offline skanning, kamera, dagens jobber, push og synkroniseringskonflikter.

4. SaaS-drift

Automatiser fakturering, abonnementslivssyklus, MRR/churn, kundesupport, databehandleravtale, eksport/sletting og tenant-offboarding.

5. Skala og sesong

Lasttest booking, søk, import og lagerkart med realistiske samtidige brukere. Vurder Redis/cache, ekte jobbkø og separat worker ved vekst.

6. Produktledelse

Etabler versjonert roadmap, release notes, feature flags, måling av aktivering og arbeidsflyter samt strukturert tilbakemelding fra dekkhotell.

Endringsregler

  • Lag ny migrering; endre aldri en allerede kjørt produksjonsmigrering.
  • Behold tenant-scope i alle spørringer, jobber, importer og API-er.
  • Oppdater OpenAPI når API-kontrakten endres.
  • Legg til tester for tilgang, demo, XSS/validering og kryss-tenant-data.
  • Oppdater denne håndboken ved nye ruter, tabeller, miljøvariabler og leverandører.

E · Kontrolliste

Teknisk og kommersiell due diligence

Følgende punkter bør være besvart skriftlig før et kjøp. Tomme eller ubekreftede punkter er ikke automatisk feil, men de er risiko som må prises og håndteres.

Teknisk

  • Testresultat fra identifisert release.
  • Produksjonsarkitektur og faktisk versjonsmatrise.
  • Backupfrekvens, retention og restore-bevis.
  • Åpne feil, sikkerhetsfunn og teknisk gjeld.
  • Lisensliste for Composer, fonter, bilder og øvrige assets.
  • Kapasitet, trafikk og observerte flaskehalser.

Kommersielt

  • Aktive betalende kunder og MRR/ARR.
  • Churn, bindingstid og utestående fordringer.
  • Supportforpliktelser og særavtaler.
  • Historiske drifts- og leverandørkostnader.
  • Rettigheter til navn, domener og markedsmateriell.
  • Hva som uttrykkelig inngår i kjøpesummen.

Personvern

  • Behandlingsgrunnlag og personvernerklæring.
  • Databehandleravtaler og underleverandører.
  • Lagringstid, sletting og dataeksport.
  • Rutine for avvik og innsynsbegjæringer.
  • Lovlig overføring av kundedata til kjøper.
  • Tilgangs- og revisjonslogger.

Akseptansetest

  • Ny tenant kan onboardes.
  • Kunde, bil, booking og hjulsett fungerer.
  • Demo kan ikke endre eller sende data.
  • Meldings- og regnskapskø logger feil.
  • Ingen kryss-tenant datatilgang.
  • Backup kan gjenopprettes på ny server.
Felter kjøper/selger må komplettere utenfor kodebasen: juridisk eier, organisasjonsnummer, domene-/registrarkonto, hostingavtale, produksjonsvolum, aktive kunder, inntekter, kostnader, supportnivå, immaterielle rettigheter og konkret liste over kontoer/nøkler som følger handelen.

3 · Prosess

Arbeidsflyter

Ny kunde og kjøretøy

  1. Registrer privat- eller bedriftskunde.
  2. Neste steg åpner kjøretøyregistrering.
  3. Hent bilinfo fra Vegvesenet ved behov.
  4. Reg.nr. normaliseres; duplikat i samme tenant stoppes i både kode og database.
  5. Ved salg flyttes bilen til ny kunde slik at historikk følger bilen.

Booking

  1. Søk navn/reg.nr. eller start fra kundekort/bil.
  2. Kunde og eventuell bil forhåndsvelges.
  3. Velg én/flere biler og tjenester.
  4. Finn fem første eller ti neste ledige tider.
  5. Kapasitet beregnes fra bukker og teknikere.
  6. Overbooking varsles rødt, men kan tillates.
  7. Kunden bekrefter via sikker lenke.

Hjul inn

  1. Finn kunde/bil og registrer sett.
  2. Mål alle fire hjul i bilvisning.
  3. Registrer mønster, skade, foto og vask.
  4. Tildel reol/hylle.
  5. Print etikett; én kode representerer hele settet.

Kontroll til mersalg

  1. Lav mønsterdybde skaper forslag.
  2. Dimensjon matches mot dekkatalog og lager.
  3. Tre alternativer: Godt valg, Bra valg, Det beste.
  4. E-post forhåndsvises.
  5. Kunden velger og godtar vilkår.
  6. Lager reserveres og jobben går videre.

Fullført jobb

  1. Kontrollpunkter fullføres.
  2. Jobb/booking fullføres eller åpnes igjen ved feil.
  3. Fakturagrunnlag opprettes.
  4. Eksport sendes automatisk eller via kø.
  5. Resultat og feil logges.

Ubekreftet time

  1. Tiden reserveres midlertidig.
  2. Kunden bekrefter/avkrefter.
  3. Syv dager før sendes varsel med 24 timers frist.
  4. Ingen respons frigir tiden.
  5. Demo/test sender aldri noe eksternt.

6 · Kundeportal

8 · API

Base /api/v1. OpenAPI: system/public/openapi.yaml og /api/v1/openapi.yaml.

14 · Utrulling

Trygg oppdatering

Ikke overskriv

  • system/.env og backupkopier.
  • Hele produksjonens system/storage/, spesielt installed.lock, opplastinger og backup.
  • Lokale system/bootstrap/cache/*.php.
  • Produksjonens system/public/storage-symlenke.
  • Denne dokumentasjon/-mappen.

Prosedyre

  1. Ta database- og filbackup.
  2. Last opp kun endrede programfiler.
  3. Behold produksjonens .env, APP_KEY og storage.
  4. Leverandør → Systemoppdatering.
  5. Installer ventende migreringer.
  6. Tøm cache og smoke-test.

Vendor: lastes bare opp når composer.json/lock endres. Database: oppdateres når nye migreringsfiler finnes; install.php kjøres ikke igjen.

15 · Produksjon

Drift, køer og backup

Kommandoer

Bookingfrister, dekkoppfølging, meldinger, regnskapseksport, billing statements, backup, demo-reset og helsesjekk.

Kø

Meldinger og regnskap lagres med status, forsøk og feil. Demo/test stoppes permanent.

Backup

Leverandør kan opprette og laste ned komprimert MySQL-backup under Admin → E-post og backup. Filer ligger privat i storage/app/backups, har rettighet 0600 og ryddes etter valgt retention. Scheduler kjører daglig kl. 03:15; minst én kryptert kopi skal oppbevares eksternt.

Diagnose

Leverandør kan aktivere maskert diagnose midlertidig og skal slå den av etterpå.

upload_max_filesize = 50M
post_max_size = 55M
max_execution_time = 300
max_input_time = 300
memory_limit = 512M

Hostingpanel/Nginx kan ha lavere overordnet grense. .user.ini kan bruke opptil fem minutter på å aktiveres.

17 · Dialog

E-post og SMS

  • outbound_messages lagrer kanal, formål, mottaker, emne, kropp, plan, status og feil.
  • Leverandør velger global transport: SMTP, lokal sendmail eller bare logg, samt systemavsender og sendetempo.
  • Hver virksomhet velger eget avsendernavn, avsenderadresse og svaradresse; e-postoppsettet kan testes fra Admin.
  • SMTP- og plattformhemmeligheter ligger kryptert i platform_settings; tenant-avsender ligger kryptert som email_sender-integrasjon.
  • Domeneshop SMTP: smtp.domeneshop.no, port 587/STARTTLS eller 465/SSL med autentisering. Masseutsending på webhotell skal bruke lokal e-posttjener og tempo maks 60/minutt.
  • Admin ser kø og kan forhåndsvise e-post.
  • Masseutsending krever markedsføringssamtykke.
  • SMS-kampanje krever egen aktivering.
  • Twilio-test bruker eget mobilnummer og er blokkert i demo.
  • Tilbudsmail viser alle alternativer; valg og vilkår skjer på sikker side.
  • Avmeldingslenke oppdaterer samtykket.

18 · Økonomi

Fiken og Tripletex

  1. Fullført jobb klargjør fakturagrunnlag.
  2. Tenant velger automatisk eller manuell eksport.
  3. Én aktiv regnskapsleverandør brukes.
  4. Adapter sender til Fiken eller Tripletex.
  5. Ekstern referanse, forsøk og feil lagres i invoice_exports.
  6. Feil kan ses og forsøkes på nytt.
DekkPilot er ikke et komplett regnskapssystem; det oppretter og eksporterer fakturagrunnlag.

19 · Support

Feilsøking

500 etter opplasting

Kontroller at produksjonens .env ikke er overskrevet, deretter DB-verdier, leverandør-diagnose og migreringer.

CSS/design mangler

Kontroller document root/rewrite, public-kopier, asset URL og cacheversjon.

Installer sier allerede installert

Det er riktig på aktiv server. Behold storage/app/installed.lock.

Import stopper

Kontroller Laravel 50 MB-grense, .user.ini, hostingpanel og eventuell Nginx client_max_body_size.

Ingen meldinger sendes

Kontroller kø, cron, mailer/Twilio og TestDataGuard. Demo/test skal ikke sende.

Vegvesen-felt mangler

Owner/admin ser feltet i eget reelt miljø; leverandør alltid; vanlig demo aldri.

Mobilmeny

Portal bruker sidepanel. Teknikermodus bruker bare bunnmeny. Oppdater begge app-shell/technician CSS/JS-kopier og layout.

DB mangler tabell/kolonne

Ta backup og bruk Leverandør → Systemoppdatering.
